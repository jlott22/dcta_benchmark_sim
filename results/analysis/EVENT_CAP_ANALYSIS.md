# Scheduler-event cap and stagnation analysis

Generated by `results/analysis/analyze_event_caps.m` from all active core and sensitivity system-performance tables.

## What the two limits mean

The global event cap counts scheduler activations. Each activation calls one robot once and may produce movement, turning, intent synchronization, replanning, idling, or a no-goal response. It is therefore not a step limit or a wall-clock timeout. The scheduler checks mission completion before applying the cap; a cap exception means the mission was still incomplete at that event count.

The known-target simulator also applies a stagnation detector at 2000 consecutive scheduler events with no change in either robot positions or the number of completed targets. The counter resets whenever a robot moves or a target is completed. This detector is checked before the global event cap, so it can terminate a no-progress run earlier; total events at termination can exceed 2000 because the threshold concerns only the current consecutive no-progress streak.

Because settings changed during the campaigns, the tables preserve recorded cap minima and maxima. At the user's request, all cross-campaign headroom comparisons use the lower historical reference of 5000 events. That conservative reference does not claim every stored run was actually configured at 5000.

The grid/robot schedule below is the present configuration default, not a reconstruction of every historical run. It can be overridden by a worker or command-line setting; notably, the current known-target grid-density worker sets 800,000 events explicitly. In the uploaded known-target grid data, failed rows record 5,000 while successful rows omit the cap, and some successful trials processed more than 5,000 events. Therefore the default-schedule multiples are scenario context, whereas only populated recorded-cap fields establish historical settings.

## Paper-ready context

"Trials were protected by a scheduler-event safety limit rather than a mission-time cutoff. Scheduler events include both movement and nonmovement activations, so the limit is not directly comparable to path steps. Because cap settings changed, we use 5,000 events as a conservative common reference and separately report populated per-run cap fields; the present adaptive default is shown only as scenario context. Successful-trial step totals and, where exported for Collaborative Visit, exact event counts provide context for the available headroom but do not redefine the cap. The known-target simulator additionally stopped runs after 2,000 consecutive events with neither robot movement nor target completion, resetting the counter whenever progress occurred. Runs reaching either safeguard before mission completion were classified as noncompletions and were not assigned artificial step penalties."

Exact values and all caveats are in `results/analysis/tables/event_cap_*.csv`.
